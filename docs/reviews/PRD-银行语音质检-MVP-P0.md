## 1. 方案摘要

建议以“3 个核心角色、7 个业务入口、1 条完整质量改进闭环”收敛首版：发现候选风险 → 人工复核 → 主管确认 → 申诉纠错 / 整改跟进 → 报表查看结果；规则与业务资源提供判断依据。

保留申诉与整改、业务资源、质量报表，缩减多级审批、专家独立工作台、班组中转、我司项目后台和高级配置。沿用当前 UI 风格及证据阅读方式。完整指标目录仍为 16 项，规则配置对应其中 10 类，不将目录完整性等同于模型实现或真实验收通过。

## 3. 背景、核心痛点与参考依据

### 3.1 当前产品基础

原项目已经覆盖客户生产台与我司项目后台、10 个角色及多套工单布局。reviews 汇总了产品、流程、指标、研发、交互与历史差异；代码有可复用的页面和样例，但部分当前文档仍描述待实现行为。

本方案依据用户明确的高保真原型定位、reviews 当前专题和公开产品资料制定。以下痛点是对现有产品的分析假设，尚无新一轮银行用户访谈或量化使用数据，不写成已验证的客户调研结论。

| 核心痛点 | 对使用者的影响 | P0 处理 |
| --- | --- | --- |
| 导航和角色多，主要任务被交付与配置功能分散 | 初次使用难以判断从哪里开始 | 三个角色有不同默认待办，七个业务入口归为三组 |
| 风险发现、最终结论、整改完成混用 | 不清楚问题是否成立、由谁继续处理 | 分开候选风险、复核、申诉、整改及其状态 |
| AI 命中难以结合上下文核查 | 误报、引用、否定和证据缺失不易解释 | 录音/转写定位、前后文、规则与资源版本同屏可追溯 |
| 角色层级过多，交接成本高 | 简单问题也需班组、专家等多次传递 | 主管直接分派质检员和整改坐席；必要的专业补证仍留出口 |

| 规则与知识依据脱节 | 不知道判断基于哪版词库、知识或 SOP | 保留精简资源维护、规则引用及历史版本 |
| 16 项体系与 10 类规则被混为一个数字 | 误以为能力漏项，或错误宣称全部实现 | 完整目录、规则入口和演示能力分别标识 |

## 4. 设计目标与成功标准

### 4.1 设计目标

1. 让主管围绕风险优先级完成分诊、确认和跟进，始终知道当前责任人与下一动作。
2. 让质检员基于完整证据给出意见，保留误报、证据不足、风险成立三种结果。
3. 让坐席能理解本人结论、提出异议、完成整改，而非只能被动接收通知。
4. 让规则、业务依据、过程记录与报表可相互追溯，支持评审“为什么这样判、处理是否完成”。
5. 用一套完整可操作的高保真原型验证这些任务，延续现有视觉风格，控制每个模块的功能深度。

### 4.2 本轮验收目标

P0 原型验收范围已冻结：七个入口按角色开放；第 8 节 T01—T18 与已采纳 D01—D05 均纳入验证。跨角色操作、列表、详情、通知、报表使用统一状态；刷新保留演示进度；重复请求不重复建案；坐席仅能查看本人授权记录。实际验证结果及限制见实现与验收记录，不将原型验证解释为生产能力达标。

业务上的复核效率、误报减少和整改效果作为后续试点观察目标；没有基线，不设置虚构的降本百分比。首版报表用于验证统计口径，示例数字不作为真实经营或模型效果。

## 5. 目标场景、假设与范围

### 5.1 目标场景

单个银行呼入客服团队，围绕业务咨询、身份核验、服务态度与敏感信息等典型场景开展事后质检，并包含轻量的通话中风险提醒。角色为质检主管、质检员、客服坐席；班组保留为人员归属和筛选维度。

假设主管可直接分派到坐席，并维护经业务确认的示例资源。未来若试点要求班组签收或专家独立裁定，再增加相应角色；当前不能据此认定主管具有所有专业裁定能力。

### 5.2 范围边界

| 范围 | P0 决定 |
| --- | --- |
| 核心业务 | 七模块均保留，每个只做主路径与必要异常 |
| 实时能力 | 演示候选告警、提醒、回执和通话结束转复核；不建设 CTI 或实时流服务 |
| 申诉与整改 | 两类独立案件、三个角色、基本补件与退回、关联暂停及恢复 |
| 规则 | 固定结构；只对明确开放的少量参数提供修改、预览和版本化生效 |
| 资源 | 词库、业务知识、SOP 三类；单条维护、草稿、影响查看、模拟发布 |
| 统计 | 一页质量报表，固定视图、筛选、下钻与 CSV 导出 |
| 排除项 | 多租户、用户权限配置平台、专家/班组独立工作台、训练平台、自定义报表、复杂审批编排、全套项目交付后台 |
| 未来真实交付 | ASR/声纹/纠错等真实模型、独立金标、真实接口、容量压测及生产权限另立研发范围 |

主管得到完整的问题处理视图，质检员得到可核验的证据与明确待办，坐席得到透明结论和纠错渠道。资源提供依据，报表验证处理结果；三者共同支撑质量改进。

## 7. 产品设计与核心功能 PRD

### 7.1 页面目录与布局

```text
银行语音质检
├─ 质检作业
│  ├─ 风险预警
│  ├─ 质检工单
│  ├─ 申诉与整改
│  └─ 通话记录
├─ 策略与资源
│  ├─ 质检规则
│  └─ 业务资源
└─ 分析
   └─ 质量报表
顶栏：角色/演示身份切换、通知；侧栏底部：演示数据重置与版本
```

主管默认进入“风险预警—待分诊”，质检员进入“质检工单—我的待办”，坐席进入“质检工单—需我处理”；无待办时显示结果快捷入口，不自动伪造任务。导航名称、分组与相对顺序一致，按权限隐藏无关入口，不为某角色重新排序；坐席顺序为质检工单、申诉与整改、通话记录。

| 页面 | 内部组织 | 主要布局 |
| --- | --- | --- |
| 风险预警 | 待分诊、跟进中、已转复核、已关闭 | 左侧风险队列，中间证据，右侧当前责任与动作 |
| 质检工单 | 我的待办、全部授权工单、已完成 | 复核意见与主管结论分区，历史与下一步分区 |
| 申诉与整改 | 单层状态页签：需我处理/进行中/已结束/全部；可见类型筛选：全部类型/申诉/整改 | 当前案件、原结论、关联案件、补件/验收记录 |
| 通话记录 | 日期、业务、班组、坐席、检测状态筛选 | 紧凑表格 + 通话详情 |
| 质检规则 | 指标分类、规则列表、版本与允许修改参数 | 列表 + 详情/编辑弹窗 |
| 业务资源 | 词库、业务知识、SOP | 列表 + 草稿编辑 + 发布确认 |
| 质量报表 | 质检概览、问题分布、坐席/班组、申诉整改 | 共享筛选，一页固定视图，支持下钻 |

所有队列即使为空也保留分类切换；返回列表保留筛选、分页和选中项。列表默认 5 条，可切换 10/20 条。相关事件通知跳到具体对象，不额外创造任务状态。

### 7.2 角色矩阵

| 能力 / 数据 | 质检主管 | 质检员 | 客服坐席 |
| --- | --- | --- | --- |
| 风险预警 | 查看管理范围，分诊、提醒、分派 | 无独立入口，工单内看关联风险 | 无独立入口，通过通知收本人提醒 |
| 通话记录 | 管理范围全部 | 分派任务及授权样例 | 仅本人通话 |
| 质检工单 | 全部管理范围，分派、确认、下发整改 | 仅本人任务，提交复核意见 | 仅本人已送达结果 |
| 申诉 | 受理、补件协调、分派、最终裁定 | 被分派后核查，提交意见 | 本人提交、补充、撤回、查看结果 |
| 整改 | 下发、调整、决定结案/退回 | 被分派后验收、补样、提交结果 | 本人接收、反馈、补材料、申请调整 |
| 质检规则 | 查看、修改开放参数、确认模拟生效 | 查看规则及版本 | 仅在本人结果内查看所引用依据 |
| 业务资源 | 维护草稿、查看影响、确认模拟发布 | 查看当前及任务引用版本，提出补充意见 | 仅查看本人任务需要的相关条目 |
| 质量报表 | 管理范围筛选、下钻、导出 | 不提供独立入口，工作页保留本人任务统计 | 不提供独立入口，查看本人结果 |
| 最终结论 | 确认或改判，必须有依据 | 提交意见，不直接改主管结论 | 不能编辑结论 |
| 历史记录 | 查看，不能直接覆盖 | 查看授权部分，追加意见 | 查看本人相关记录，追加材料 |

动作可用性共同取决于角色、数据范围、对象状态及当前责任分工。每个对象保留一名主责任人；登记的补件执行人可以在授权子任务中追加材料，但不能因此取得复核、裁定或结案权限。原型用前端实现此约束，不将角色切换器描述为真实身份认证。通知、搜索、导出、详情链接与统计均使用相同的数据范围。

运营统计并入主管；班组中转缩为主管直派；专家不设独立账号。存在规则/业务边界争议时，主管登记待补依据、来源、期限和责任人，补入意见后再判断；无法补足按证据不足关闭，不强制给出成立结论。

### 7.4 质检架构与数据关系

| 层 | 业务职责 | 原型承接方式 |

```text
结论版本 ── 申诉 Appeal ── 需要时创建申诉核查任务
成立结论版本 ── 整改 Remediation ── 材料 / 样例 / 验收轮次

规则引用快照 ── 固定规则版本 + 固定资源版本
检测批次开始时固定快照；历史重检另建批次
事件 Event 关联业务对象，驱动通知 / 待办 / 报表
```

主管可从通话记录发起人工抽查，填写检查项范围、质检员、要求和期限；任务直接关联通话，风险列表初始可以为空，不伪造 AI 命中。抽查结论分为“检查范围内未发现问题”“发现问题”“证据不足”；未发现问题须注明已查范围，经主管确认后完成任务，不创建风险或误报记录，也不表示整通或 16 项全部合格。发现多个问题时分别记录人工发现及证据、逐项确认和按需整改；任务结论是这些问题的汇总，不替代逐项结论。自动检出与人工发现分别保留来源，同一事实经确认后只用一个问题编号统计，来源关联可以多个。

首版每条自动候选风险最多建立一个进行中的初次复核工单；人工抽查任务可先无风险，随后关联零条或多条人工发现。任务类型区分候选复核、人工抽查、申诉核查，检查范围必填；申诉核查另需引用被检查结论版本，初检和无发现抽查不强造结论版本。同一任务补充核查按轮次追加；申诉需要重查时新建关联核查任务，原初次复核工单保持已完成。不同案件可互跳，各自维护状态。

对象关系补充：人工抽查 ReviewTask 直接引用 Call，Finding 可以为空；发现问题后逐项建立/关联 Finding。申诉只引用被申诉的问题结论版本，整改引用成立问题及其结论版本。人工抽查任务的汇总结果不是某一条风险事实结论。

同一通话可有多个风险；同一事实由多个检测条件支持时使用一个主指标，其他标为关联依据，不自动重复计为多个独立违规。同一请求标识的重复动作返回已有对象。候选复核按风险编号与任务类型防重复；人工抽查按通话、检查项范围与进行中状态防重复；申诉按被申诉结论版本防并行重复；整改按来源问题、结论版本和处理目标防重复。需要新增检查范围或轮次时由主管明确发起并记录理由，不把合法的新任务误当重试。P0 不提供跨通话合并工单或批量整改案件。

所有活动对象有当前责任人、下一动作和必要期限；结论、生命周期、严重度、检测执行状态独立显示。历史追加不覆盖；失败、未知、未检测不等于无风险。通知已读不代表业务完成，坐席已读不代表认可结论。

联动与过期动作：申诉撤回、不受理或直接办结时，取消尚未完成的关联申诉核查任务，保留已提交意见并关闭其待办；取消不产生新的风险结论。结论版本、整改标准或任务责任人变化后，旧表单提交须提示上下文已变化，保留输入并重新核对。原型在同一次状态更新中完成任务、责任、通知与关联案件变化，不要求建设真实事务服务。

| 对象 | 主要状态 | 当前责任与出口 |
| --- | --- | --- |
| 候选风险 | 待分诊、跟进中、已转复核、已关闭 | 前两态由主管负责；跟进须说明是补证或提醒；关闭保留误报/证据不足原因 |

风险逐项结论为风险成立、误报、证据不足；人工抽查任务还可汇总为“检查范围内未发现问题”，不将其记成误报。任务完成须检查范围内所有必查项已有结果或明确证据不足原因，每个成立问题已指定后续去向。成立后的去向为无需整改结案或已转整改；两种均可完成本次复核，独立整改通过验收并经主管确认后才算整改完成。

### 7.7 核心功能 PRD：通话与证据（F01）

使用者从列表、预警、工单或报表进入同一通话详情。列表字段包括通话编号、业务、坐席/班组、起止时间、时长、检测状态、候选风险数、最新人工结论概况。

详情提供录音播放/暂停、进度定位、角色转写、命中高亮、前后文、规则与资源版本，以及关联风险、工单、申诉、整改。点击证据时间跳到对应音频与话轮；同一通话多风险切换不重新创建通话记录。

样例音频可使用可合法使用的合成素材。无音频的特定样例明确显示缺失，转写仍可阅读；不以会移动的进度条冒充真实回听。原始转写与修订文本分开保存，P0 不提供通用逐字稿编辑器。

验收：不同入口打开同一对象内容一致；至少一条完整主流程能实际回听并定位；失败/未检测与正常未命中可区分；坐席搜索和直接链接均不能看到他人记录；CSV 与当前筛选一致。

检测状态的示例契约：未开始为待处理；至少一个必需项已开始而整批尚未结束（含排队/待重试）为处理中；所有必需项都执行成功为已完成；全部结束但部分必需项失败为部分失败；全部必需项失败为失败。成功执行但无法判断与执行失败分开：前者的业务结果可以是证据不足。必需项集合随场景固定，不默认要求 16 项逐通检测。人工抽查结果不把自动检测失败改成成功；已完成也不等于没有风险。

人工抽查可关联同通话已有问题，禁止重复关联或抢占其他进行中复核。每个正式结论版本保存选用证据、规则版本和检测批次；详情区分原始命中与各版结论，申诉和整改固定引用对应版本。旧记录未保存独立证据时明确提示，不伪造回填。

### 7.8 核心功能 PRD：分诊与实时提醒（F02、F03）

主管选中候选风险后查看业务场景、严重度、证据、当前阶段及下一动作。“关闭候选”“要求补充材料”“转人工复核”直接展示；通话中另显示“提醒坐席”。关闭表单区分误报和证据不足，补件直接进入缺项表单。阶段主动作以实心按钮突出，不增加“更多操作”入口。

关闭须填写原因类型、具体说明和证据；补证须填写缺失项、执行人、期限和复查触发条件。分派须填写有效质检员、复核要求和未来期限，保存后同时更新主管队列与质检员待办。

提醒仅在通话未结束时可用，填写提醒内容、接收坐席，可预设复核人。坐席收到后可已读、反馈执行情况或提出提醒异议；发送、送达、已读、执行反馈分开记录。原型用场景事件模拟通话结束，不把“挂断客户电话”设计为主管业务按钮。

结束事件封存当前证据。已存在有效分派时自动复用/创建对应复核；分派不存在或失效时进入待主管补全，不随机指定人员，不静默关闭。同一风险和轮次重复收到结束事件只保留一个任务。

验收：误报与证据不足分别查询；补证到期有待办并可退出；提醒不是最终违规；回执缺失不阻断转复核；已结束通话无法再次发实时提醒；空队列仍可切换分类。

提醒同时进入本人“质检工单”的常驻队列与待办通知。坐席页分为“需我处理 / 全部事项 / 通话提醒 / 质检结果”，未读提醒计入需我处理；标记已读只清除阅读待办，仍可在全部事项和通话提醒中查看、反馈或提出异议。执行反馈为可选动作，不新增强制反馈任务；提醒与正式结论分别记录，不互相替代。

### 7.9 核心功能 PRD：复核与主管确认（F04、F05）

质检员仅处理分派给自己的有效任务，按任务类型和检查范围提交意见、理由及证据；候选复核逐项判断风险成立/误报/证据不足，人工抽查另支持范围内未发现问题。保存草稿不改变责任人；提交后进入待主管确认。材料不足时提出缺项、执行人及期限，由主管组织并回流。申诉核查只向申诉案件提交意见，不直接发布新结论或再建整改。

主管可以确认或退回补充核查；改变质检意见须记录理由和证据。依据不足时先补证，不强制判断成立或误报。最终结论通知坐席并留在本人结果中。申诉核查意见只在申诉案件裁定后形成结果，不重复发布；D03 已采纳：默认优先选择另一名质检员，原复核人核查须记录无人可替代的原因。

风险成立后提供“无需整改结案”和“下发整改”两个出口。无需整改须记录原因，例如当次已经纠正并有证据、仅需记录或已存在关联整改；已有关联事项继续保留自己的状态。下发整改弹窗一次完成责任坐席、目标、期限、标准、验收质检员及复测要求，提交即创建案件并完成复核，不生成额外待下发草稿。

验收：无整改的成立风险仍计为成立且可申诉；误报不生成整改；证据不足不计误报；仅记录已读不会变更人工结论；工单完成不等于关联整改完成。

复核保存与提交共用表单；通话中可留草稿，结束后才正式提交与送达结论。主管逐问题选择整改或无需整改理由，可复制上一问题要求。有效申诉期间禁止从原问题另行改写正式结论，新证据进入当前申诉。主管待分诊事项只进入风险预警，工单队列及导航按对象实际所属页面计数。

### 7.10 核心功能 PRD：申诉（F06）

坐席仅可对本人最新已送达的风险成立或部分成立结论正式申诉，必填理由并关联有效证据。误报、证据不足等结果通过补充意见与主管补证跟进处理。同一结论版本同时只允许一件有效进行中的申诉；撤回、不受理后可补正重提，不消耗实质裁定机会；实质办结后同版不无限重复，新证据由主管登记跟进，新不利结论版本可再次申诉。以上为已采纳 D01。

主管受理、退回补充或说明不受理原因；受理后可以依据充分材料直接裁定，或分派质检员核查。受理前补件和核查中补件均由主管提出明确缺项；坐席重提后先回主管，再交原核查人，保留来源阶段和轮次。

裁定支持维持原结论、改判为误报、改判为证据不足、调整成立范围。原结论和证据保留；维持沿用原结论版本，仅改判新增版本。调整成立范围时同步修改整改目标与标准，旧验收意见不可关闭新标准任务。坐席可撤回尚未办结的本人申诉；撤回不等于承认原结论。

P0 不设置 3/1/2/3 工作日制度。补件和核查期限由主管指定，逾期提示而不自动判败；申诉创建时的初始跟进期限为原型演示值，可由主管调整，并不构成客户 SLA。重提与同版实质办结限制按已采纳 D01 执行。复杂复议与窗口配置后置。

验收：重复点击不重复建案；补件不绕过主管；核查意见不直接变成最终裁定；改判保留历史、更新有效结论及报表；非本人不能提交。

受理表单提供“受理并分派”和“受理并裁定”：一次提交内完成受理和下一动作，第二步失败则整体不生效，重复请求不重复创建对象。核查中补证等待坐席回复时，父申诉和原核查不计主管办理待办；回复后只在原申诉产生主管接收补证待办，接收后恢复原质检员核查。等待状态可以在进行中查看，具名执行人与正式意见责任分开。

### 7.11 核心功能 PRD：整改与暂停（F07、F08）

下发后坐席直接接收任务，查看问题、目标、完成标准、期限和所需样例。要求不清楚或不可执行时向主管申请调整，记录修改版本，不退回已完成的原复核工单。坐席提交文字说明、关联样例或预设附件后进入待验收。

质检员检查材料与整改后的相关通话样例，给出通过、不通过或证据/样例不足。样例不足保持待验收并标记待补材料：质检员仍是验收主责任人，坐席是具名补件执行人，双方待办分别显示核验跟进和补件；每次补件有缺项、期限、提交记录及回到质检员的出口。不通过后进入待主管处理（待退回），通过后进入待主管处理（待结案）；两者不能共用“已通过”标记。主管可要求再核查，不能绕过质检员验收直接通过。

首版不固定“7 天、10 通”等客户制度。主管下发时填写观察要求与所需样例数量，使用演示值；完成标准修改须保留理由及版本，相关待验收或待结案任务须先回到质检员确认；旧验收意见保留为针对旧标准的历史，不可拿旧意见直接关闭新标准任务。示例用整改后的通话/材料表现改善，不能把提交培训说明自动算作效果达标。

有效申诉提交后，若存在未结束的关联整改，则设置“申诉暂停”：保存暂停前阶段、责任人、原期限、暂停起点及是否已逾期；允许追加说明，禁止进入验收通过或结案。重复暂停事件不重复累加；如存在多个暂停来源，记录来源集合，仅在全部解除后恢复，重叠区间按时间并集计时。整改材料补充可以继续，暂停期内的意见只能保存草稿，不得发布通过或结案。

维持、撤回或不受理后恢复整改原阶段，按实际暂停时长顺延期限，保留暂停前逾期标记。改判为误报时终止未完成整改并注明误报原因。D02 已采纳：改判为证据不足时，以“原整改依据不充分”终止旧人员整改，不计完成或误报；能补证时另建具名、有期限的补证跟进，后续重新确认成立须新建关联整改。调整成立范围时更新目标和标准并重新核验。已结案整改保留历史，追加来源结论改判标记并在报表单列。

验收：申请整改只产生一件案件；补材料不会新建重复整改；没有合格验收不得结案；暂停期间不能结案；恢复时长可复算；终止不计入完成；已逾期事实不被申诉清除。

验收统一从“验收处理”进入同一表单，提供“保存草稿 / 提交验收意见”。草稿保存结果、说明、补件期限（如适用）、轮次、标准版本、保存人和时间；刷新或重开恢复已保存内容。轮次、标准或验收人变化后，旧稿保留为参考，当前验收人须确认已核对本轮材料与标准才能再保存或提交。旧稿归档，旧验收人失去写入权限。暂停或等待补件时可继续保存草稿，正式验收仍受状态约束。

普通补证改判与申诉改判共用整改终止处理：同步结束未回复、已回复待接收的失效补件，显示“随整改结束”及原因，保留要求、原回复和材料；终止后的旧页面不能继续回复或接收。维持结论则恢复原补件。退回前保存本轮标准、材料、样例与验收意见；变更期限前记录已发生的逾期及调整前后值。

### 7.12 核心功能 PRD：质检规则（F09）

提供对应 10 类指标的分类入口，规则列明名称、主指标、适用业务、判断说明、严重度、证据要求、关联资源、版本。关键词检出/禁用词、情绪识别/消极情感分别呈现；关联指标不重复计数。

主管只能编辑该规则明示开放的字段，例如静默时长阈值、适用业务或提醒触发参数；无开放字段的规则只读。规则结构、主指标、检测器编排、证据契约不可编辑，不提供新建或删除规则逻辑入口。

参数编辑 → 本地字段校验 → 修改差异与引用预览 → 查看明确标为示例的预设检查 → 确认模拟生效。D05 已采纳，开放字段见下表与实现记录：R-AC-003 静默阈值，单位秒、默认 15、允许 3–60 的整数；R-INT-001 业务范围，默认全部业务，选项为全部业务/账户查询/信用卡/转账汇款；R-AL-001 提醒触发，默认高风险候选，选项为高风险候选/所有候选/关闭提醒。其余规则只读。预设检查失败保留草稿；发布新增版本。在途检测固定开始时快照，新启动使用新版；历史重检显式新增批次，不修改旧结果引用。

验收：仅主管能修改白名单字段；取消不改变生效版本；非法参数阻止提交；发布后列表、详情、引用关系一致；示例检查明确属于原型模拟。

### 7.13 核心功能 PRD：业务资源（F10）

保留词库、业务知识、SOP 三类。词库条目含词语、分类、适用角色和例外说明；知识条目含问题/主题、答案、业务范围及依据；SOP 含步骤顺序、必要步骤和允许例外。每类均有资源编号、状态、版本、更新时间和引用规则。

主管新增条目或从当前版本创建草稿；编辑、保存后记录出现在列表，不能只弹成功提示。基础校验包括必填、同范围重复词条、空 SOP 步骤及缺失引用。质检员只读并可提出补充意见，坐席仅查看本人案件引用的必要内容。

发布前显示内容差异、受影响规则、预设检查结果及生效范围。确认发布后只生成新资源版本；另行选择受影响规则并确认切换引用，才为所选规则生成新的引用配置版本或快照；不原地修改已有 RuleVersion 指向的资源。新启动的示例检测取新快照，已开始的检测和历史案件保留旧快照；历史资源仍可从旧案件查看。检查失败保留草稿并给出修正入口；不物理删除仍被历史引用的版本。P0 不建设多部门审批、真实解析任务或模型训练。

验收：三类各至少一个可维护示例；草稿/生效/历史可区分；发布后规则引用不变，确认切换后的新检测引用新版，旧案例保留旧版；不能用资源维护绕过固定规则逻辑的权限。

### 7.14 核心功能 PRD：质量报表（F11）

### 7.15 核心功能 PRD：通知与统一交互（F12）

分派、补件、意见提交、结论送达、申诉、整改验收和资源发布生成对应事件。通知包含对象、动作、摘要和发生时间，点击进入有权限的具体位置；已读仅改变通知状态。失去权限或对象不再待办时说明当前状态，不让旧通知执行过期动作。

提交前验证必填与未来期限；提交期间防重复。成功必须伴随真实的前端记录变化；失败保留输入并给修正/重试入口；取消不写入记录。非责任人只读并显示等待谁处理。

责任补充：补件执行人是限定动作的例外，只能提交对应材料；质检员和主管的正式意见仍由当前主责任人提交。主管可对未完成任务转派并记录原因；原责任人的未提交草稿保留但失去提交资格。各期限标明日期/时间与 Asia/Shanghai 时区，演示状态使用统一时钟，避免固定历史种子到期后全部意外显示逾期。

全局保存演示状态；刷新、角色切换后继续流程。重置数据需提示将清空本轮演示操作，恢复预设样例。种子快照显示为示例初始状态，时间线仅把实际操作写成已发生事件。

默认队列按当前可办理阶段计算，等待他人的事项留在进行中。补件嵌入原案件；已读提醒、知悉结果、接收整改为单次操作。兼容旧演示状态：补充结论证据快照、补证申请、整改轮次和期限记录；已结束整改的遗留未完补件恢复为只读结束状态。旧版仅保存的验收文字缺少轮次等依据，作为待核对参考；已经丢失的旧历史不伪造恢复。本轮不清空浏览器演示进度。

沿用当前浅灰画布、白色内容面、细边框和紧凑表格。橙色用于选中与证据，黑色用于主要动作，绿/红配文字表示结果和风险。当前画布 #F6F7F8、正文 #171717；通用面板圆角 10px。报表使用边框 #E4E7EB、图表强调 #EF7927、文字强调 #B75717，数字等宽；以 27px 摘要数字、15px 分区标题和 12–13px 说明建立层级。继承字体与组件尺寸，根据实际页面可读性调整，不重做品牌风格。

固定侧栏与顶栏，常用筛选和当前动作直接展示。通话列表只负责查询；点击编号或查看详情进入独立详情视图，返回保留筛选和页码。详情显示通话状态，不把没有待办误写成“已办结”；原话、判断依据和引用快照直接展示，检测批次和历史轮次可按需展开。

规则与资源采用“左侧列表、右侧完整详情”。规则标题下优先显示参数配置：当前值、单位、范围与业务作用；点击参数旁的编辑按钮就地进入编辑态，同时显示修改原因、保存草稿和取消。固定规则与只读角色给出明确说明。继续仅开放静默阈值、适用业务、提醒触发三个白名单字段，不扩大规则搭建能力。

草稿通过新旧值对照、检查结果、发布按钮形成连续链路。未保存参数切换模块、规则或版本时保留输入并就近提示；保存草稿不直接生效。新增资源保存后自动定位到新条目。历史版本只读，先返回当前版本再修改。

正文与表单采用清晰的字号和对比度；弹窗使用浏览器原生 dialog，支持焦点限制、Escape 和焦点恢复。390px 窄屏在列表与详情之间切换，不挤压三栏；保留可见返回入口。按钮不做缩放按压动效，结果提示采用 200ms 透明度反馈；高频导航与数据即时响应，键盘操作不附加动效，减少动态效果设置保留短暂淡入淡出。

队列翻页同步本页选中对象与详情；日期倒置时就近报错、暂停导出，并可直接交换日期。以上分别关闭复评 N05 与 N06。

### 9.3 已采纳：建议方案、影响与最小验证

以下保留 D01—D05 的审查问题、建议和替代方案，作为决策依据。用户于 2026-09-12 明确回复“可以，按照这个执行，迭代mvp-p0代码”，已采纳五项建议；替代方案未采用。旧 reviews 的 D 类问题在 8.3 标为“旧 D”，与本次决策区分。

#### 9.3.1 D01：哪些结果可以正式申诉，撤回和不受理后能否重提

**问题**：原文允许对误报、证据不足补充意见，但裁定选项主要面向成立风险；“每版一次”又没区分办结、撤回和不受理，可能把没有实质处理的案件永久挡在门外。

**原方案合理处与失效条件**：限制并行案件可以防重复；如果任何结论都能正式申诉但没有对应改判出口，或撤回也耗尽机会，则流程失效。

**建议**：正式申诉针对已送达且对本人不利的成立/部分成立结论；误报、证据不足通过补充说明与主管追加核查处理。限制同版本一件进行中案件；撤回、不受理不算实质裁定，可补齐后重提。实质办结后同版本不自助循环申诉，有新证据走主管补充核查；形成新的不利结论版本后可申诉该新版本。

**替代方案与影响**：允许所有结论正式申诉，但必须补齐各结论之间的改判、转核查和二次通知规则，范围更大。建议方案减少案件分支，同时保留补充事实的入口。

**最小验证与否决条件**：用成立、误报、证据不足、撤回、不受理、再次产生不利结论六个样例逐个走查；如果有本人合理异议找不到入口，或同版本能无限重复冻结，需调整方案。确认内容：是否采用以上正式申诉范围及重提规则。

#### 9.3.2 D02：申诉改判为证据不足时，关联整改如何处理

**问题**：原文把改判为误报和证据不足都自动终止整改；两者事实含义不同。终止可能中断仍需补证的事项，继续整改又可能将未确认问题当成坐席责任。

**原方案合理处与失效条件**：没有成立依据时不应继续要求人员整改；如果把终止整改显示成“已证实误报/无需继续核查”，则方案失效。

**建议**：终止基于原成立结论的本次人员整改，理由明确为“依据不足”，不计为整改完成或误报；如果主管认为可以补足证据，另建有责任人和期限的补充核查，后续重新确认成立再创建关联新整改，不复活旧验收结论。

**替代方案与影响**：保持原整改暂停，设置补证期限；证据补齐后恢复或终止，需持续管理暂停积压。建议方案状态更清楚，但可能多一件关联新整改；两种都需保留旧历史。

**最小验证与否决条件**：分别用“证据永久缺失”和“可补取另一段录音”走查；如果未确认责任仍被统计为坐席逾期，或旧失败验收被新结论覆盖，方案不通过。确认内容：终止原整改并另行补充核查，还是保留暂停。

#### 9.3.3 D03：申诉由谁重新核查，是否优先避开原质检员

**问题**：三角色不等于每个角色只有一个人。当前没有约束申诉是否继续分给原复核者，可能出现同一人重复确认自己的原意见。

**原方案合理处与失效条件**：原质检员熟悉证据、处理更快；如果演示的申诉必须由另一人核查才被业务认可，而界面只有一位质检员，就无法演示可信的纠错过程。该业务安排已按 D03 建议采纳，不构成新增的生产合规要求。

**建议**：角色仍为三个，质检员至少提供两个演示身份；申诉分派默认优先其他质检员，主管仍做最终裁定。无其他可用人员时允许原质检员补核，显示同人核查并要求主管写明选择理由，不默认强制新增专家角色。

**替代方案与影响**：允许任意质检员，不提供优先避让；交互更简单，但评审时需明确接受这一安排。建议方案只增加身份样例与分派提示，不增加导航。

**最小验证与否决条件**：用一次原结论错误的申诉让两位评审者走查；如果所有参与者仍看不出初检、重检和裁定由谁做，分派及历史展示需重做。确认内容：是否优先其他质检员，允许何种回退。

#### 9.3.4 D04：首版是否展示按时完成率，以及暂停如何进入分母

**问题**：按有效期限归期、暂停单列与保留历史逾期尚未形成一套可复算规则。例如昨天已逾期的任务今天申诉暂停，若直接移出到期群，按时率会无故上升。

**原方案合理处与失效条件**：有效期限能体现申诉暂停的公平性；如果延期/暂停使已发生的逾期从报告消失，或同一截止时刻无法手算复现，则统计失效。

已采纳建议：P0 保留任务总量、当前逾期、暂停、延期、按时结案数量与明细，不显示按时完成率。后续如需比例，先确认到期群、暂停、取消、跨期及零分母规则，再建立固定样例验证。

**替代方案与影响**：本轮就保留比例，但须同时选定到期群使用原期限还是调整后期限，并定义暂停、取消、跨期和零分母规则。建议方案保留质量报表价值，减少容易误导的比例；不会删掉报表模块。

**最小验证与否决条件**：准备按时完成、逾期未完成、到期前暂停、到期后暂停、跨期关闭、取消和零分母七条记录；如果仅执行暂停操作就抹去既有逾期，则比例口径不通过。确认内容：首版先展示数量，还是本轮补齐比例口径。

#### 9.3.5 D05：首版具体开放哪些规则参数，模拟发布做到多深

**问题**：原文只举“阈值、范围、提醒参数”等例子，没有逐条字段与范围，开发可能做成任意配置器；预设检查也容易被误解为参数变更后真实计算的效果。

**原方案合理处与失效条件**：少量可编辑参数能体现产品适配能力；如果无法列出固定字段、校验和展示结果，或修改任意值都显示相同的“效果提升”，则本轮演示失效。

**建议**：规则模块只开放静默规则的时长阈值、指定规则的适用业务、指定提醒规则的触发选项三类示例字段；各字段在实现前写明单位、示例默认值与上下界，其余只读。三类业务资源保留单条草稿、字段校验、差异与引用预览、确认模拟发布；检查结果明确为预设场景，不增加审批流或真实模型检查。

**替代方案与影响**：规则参数本轮全只读，资源仍可维护；更快但较难验证参数操作体验。建议方案保留可操作性，以固定字段清单限制范围，不影响 16 项/10 类目录。

**最小验证与否决条件**：用一个合法值、一个越界值、一次取消、一次发布和一条历史工单走查；如果越界仍能保存、取消改变版本或旧工单跟随新版变化，则不通过。确认内容：是否采用这三类开放字段与简化发布深度。
